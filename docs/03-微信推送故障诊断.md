## 两处真实修复（有效）

### 1. 必须同时设置 `OPENCLAW_HOME` 与 `OPENCLAW_STATE_DIR`

```
只设 OPENCLAW_HOME   → Error: Unknown channel: openclaw-weixin
两个都设             → 正常返回 {"action":"send", ...}
```

插件与账号状态分别从这两个目录解析。relay 的 systemd 单元本来就两个都设，
这正是它能工作的原因。已写进代码注释与部署文档。

### 2. 给 agent main 补上 message 工具

```json5
{ agents: { list: [ { id: "main", tools: { alsoAllow: ["message"] } } ] } }
```

用 `alsoAllow`（增量白名单）而非 `allow`，不覆盖既有策略；配置已备份为
`openclaw.json.course-bak-<时间戳>`。效果：消息从「完全没进网关」变成「进到通道层」。

## 已知前提：会话窗口

插件日志每次出站都写：

```
sendWeixinOutbound: contextToken missing for to=<目标>, sending without context
```

原因：contextToken 由微信 API 随**每条入站消息**下发，保存在**网关进程**内。
而我们通过 CLI 发送时，CLI 因设备授权未批准而**回退到本地处理**，本地实例没有这份凭证。

因此出站实际依赖微信侧的会话窗口：用户最近发过消息 → 窗口开着 → 送达；
否则微信丢弃，而我们无从得知（CLI 仍然返回成功）。

**这对"每天推送笔记链接"是真实风险**：笔记发布时间与用户上次说话的时间无关。

## 待人工处理（二选一）

### 方案 A：修复 CLI 设备授权（小改动，让出站走网关）

CLI 设备身份变更后需重新批准，而批准又要求先连上网关，形成死锁：

```
gateway closed (1008): pairing required: device identity changed and must be re-approved
```

注意 `openclaw devices list` 走本地回退，会显示"设备已配对"——那是本地视图，
与网关侧要求重新批准并不矛盾，容易误判。

```bash
ssh -L 18789:127.0.0.1:18789 -i ~/.ssh/lawtech-tencent ubuntu@124.222.111.108
# 浏览器打开 http://127.0.0.1:18789/ ，在设备页面批准待处理请求
```

批准后 CLI 可连上网关，出站将带着 contextToken 发送，不再依赖会话窗口。

> Control UI 当前 `allowInsecureAuth=true`；若要经隧道公网暴露需先评估。

### 方案 B：让发送在网关内部完成（最稳，工作量更大）

写一个 OpenClaw 插件（类似既有的 law-tech-wechat-relay）在网关进程内消费本机账本并投递，
彻底不依赖 CLI 的设备授权——凭证本来就在网关进程里。

### 方案 C：恢复 cli.law-tech.dev 的用途

实测 `cli.law-tech.dev → :3001` 与 `mypilot.law-tech.dev → :16321` **两个后端都没有服务在跑**。
若 `:3001` 原本是控制台入口，可把 ingress 改指 `127.0.0.1:18789`；但需先关掉
`allowInsecureAuth` 再公开。
