## 1. 链路总览

\`\`\`
转录稿 raw-transcript.md（1320 行 / 约 4.6 万字）
  │
  ├─[1] generate-outline   角色 outline      模型读全文 [Lx] 行号 → 连续无缺口的大纲节点
  ├─[2] 大纲确认门         autoApproveOutline（默认 true = 自动通过，链路全自动）
  ├─[3] plan-nodes         程序确定性切分（12000 字 / 200 行 双阈值，可用 --node-split-* 改）
  ├─[4] write-node ×N      角色 writer       一次一个节点；同批可与其他节点的审查并发
  ├─[5] review-node ×N     角色 reviewer     独立审查：只回答"要不要重写这一段"
  ├─[6] revise-node        角色 revision     只回应 blocking 问题，最多重写 2 次
  ├─[7] assemble           角色 splicer      机械拼装 + 生成接缝段（概览/章节总结/自测/知识连接/附录）
  └─[8] final-review       角色 finalReview  终审：跨节点矛盾、重复、术语一致性
       ↓
  <课次名>.md + notes-run-summary.json + lesson-state.json → 账本推进到 notes_ready
\`\`\`

## 2. 每一步的代码位置与约束

| 步 | 角色 | 代码位置 | 约束 |
|---|---|---|---|
| 大纲 | outline | \`ai-adapter.mjs\`，校验 \`node-lifecycle.mjs:assertOutlineCoverage\` | 必须从 L1 开始、无缺口、覆盖到最后一行，否则抛错 |
| 缺口修复 | outlineRepair | \`task-runner.mjs\` | 只覆盖 \`coverageGaps\`，不改已有大纲 |
| 大纲门 | — | \`pipeline.mjs:applyTaskAction('save-outline')\` | true → \`outline_approved\`；false → 停在 \`outline_review\` |
| 切分 | — | \`node-lifecycle.mjs:planNodes\` | 确定性：同一大纲每次切出的边界一致（断点续跑的前提） |
| 写作 | writer | \`task-runner.mjs\` + \`worker-tasks.mjs:writerTask\` | 输入 = 本节点 lineRange 转录原文 + **全课结构表（各节标题/分工/类型，标出当前节）** + 上一节末尾 800 字 + 下一节目标；要求开头写"节与节的关系"而不是"接下来讲" |
| 审查 | reviewer | \`task-runner.mjs:validateReview\` + \`node-lifecycle.mjs:applyNodeReview\` | 报告必须对应当前草稿版本，否则视为"未审查" |
| 重写 | revision | \`worker-tasks.mjs:revisionTask\` | 上限 \`maxAutoRevisions=2\`；用尽后**带警告放行** |
| 拼装 | splicer | \`assembly.mjs:assembleFinalNote\` | 硬校验：必须含每个已批准节点正文 + 不得残留 \`{{占位符}}\`；按 \`kind\` 把事务/发散小节排到附录 |
| 简报 | brief | \`brief.mjs:generateBrief\` | 只读成品笔记；简报少于 60 字判为无效 |
| 终审 | finalReview | \`node-lifecycle.mjs:applyFinalReview\` | 四条出口，见 §5 |

## 3. 审查怎么判定（2026-09-24 精简后）

- **不再打分**。旧的五项评分（coverage/grounding/logic/detail/sourceCoverage）+ 阈值 75 +
  下限 \`max(45, 阈值-20)\` + 十分制归一化全部删除。分数是模型的自报感受，不稳定也不可解释，
  真正的判据本来就在问题清单里。
- **判定只看 issues 里有没有 blocking**：有 → \`revise\`（重写这一段）；没有 → 通过。
  模型自报的 \`decision\` 只作为记录，不作为判据——这样"模型说 revise 却列不出 blocking"
  不会触发一轮无意义的重写。
- **不再有人工门禁**。\`human_review\` 这个词仍被接受（模型有沿用习惯），但按"重写这一段"处理。
- **不再有"上游问题阻塞下游、上游修好下游重审"**。那是反复确认那一类开销；
  跨节点一致性交给终审一次性检查。
- 终止条件：每节点最多重写 2 次 → 带警告放行；终审整篇修订最多 1 次；空闲即停。

## 4. 并发与断点续跑

- 同一批里彼此独立的任务并发执行：**写下一个节点 + 审查上一个节点**（默认合计 3 条，
  审查最多 2 条）。参数：\`--concurrency\`、\`--review-concurrency\`。
- **每一步把课次状态写入 \`<输出目录>/lesson-state.json\`**（临时文件 + rename 原子替换），
  内容是完整课次对象：大纲、每个节点的草稿与版本、每份审查报告（含 token 用量）。
  手工运行用 \`--resume\` 续跑，自动链路（\`cycle\`）默认续跑。
- 这不是可选项：一次 16 节点的课要跑几十次模型调用，中途丢掉就全都要重付。
- 失败处理：单个任务失败只记一次失败并继续；同一任务连续失败超过 \`maxTechnicalRetries\`（默认 2）
  或连续 3 批任务全失败则整轮停下并如实报错（凭据/配额/网络这类系统性问题不该继续烧钱）。

## 5. 终审的四条出口

1. 问题能定位到节点，且该节点还有重写额度 → 退回该节点重写；
2. 问题定位不到节点（整体结构、跨节点重复）→ 整篇修订，受 \`maxFinalAutoRevisions=1\` 约束；
3. 两种额度都用尽 → **带警告放行**（\`autoAcceptedWithWarnings\`）并记进质量报告；
4. 通过 → \`completed\`。
