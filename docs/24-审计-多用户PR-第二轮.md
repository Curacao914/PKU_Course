# 一、结论

## 高

### H-N1（高，功能/兼容；非提权）law-tech：OWNER 显式迁移在仓库里没有可达路径

- **位置**：`app/api/account/migrate-owner/route.js:20-21`；`lib/db/migrations/20261003121000_multiuser_security.sql:63-65`；无任何迁移/代码写 `profiles.email`。
- **可复现条件（三条互相叠加，全部有据）**：
  1. 路由要求 `profile.email === email`（`route.js:21`）。而**仓库里没有任何地方给老 profile 写过 `email`**：
     `ensureProfile` 历史与现在都只写 `{clerk_user_id, role}`（`git show 71c3b19:lib/server/supabase.js` → `insert({ clerk_user_id, role: 'owner' })`）；
     迁移里对 `profiles.email` 只有 `ADD COLUMN IF NOT EXISTS` 与 `ALTER COLUMN ... DROP NOT NULL`，没有任何 `update ... set email`；
     `link_legacy_owner` 只写 `notification_email`，不写 `email`。→ 若线上两条 owner 行的 `email` 是 NULL，路由对任何人都返回 403 `LEGACY_OWNER_REQUIRED`。
  2. 若运维手工把 owner 的 `email` 补上，则走正常注册流程拿 Supabase 账号会撞 `idx_profiles_email_lower`（对账文件 3483 行，UNIQUE lower(email) where email is not null）→ 见 M-N2：注册直接 500。
  3. 若改成用注册流程建号（会生成一个 member profile 且带 `auth_user_id`），再调 migrate-owner → RPC 撞 `idx_profiles_auth_user_id`（UNIQUE partial）→ 返回 409。**这条我实测过**（PGlite）：
     ```
     link_legacy_owner when supabase uid already linked elsewhere -> RAISED: duplicate key ... idx_profiles_auth_user_id
     rows sharing that auth_user_id: [{"id":"…","role":"member","has_clerk":false}]
     ```
     即「失败关闭」是对的，但这条路径**永远走不通**。
- **实际影响**：交接文档描述的唯一 OWNER 迁移入口，实际操作前提是「有一个尚未关联 profile 的、已验证的 Supabase 账号」——这个状态在应用内**没有任何入口可以制造**（只能 Supabase Dashboard / Admin API 手工建号），文档没有写这一步，也没有 UI 调用该路由（`grep migrate-owner` 只有路由本身）。结果：OWNER 只能继续用 Clerk 登录（**不影响现有 OWNER 可用性**，也**不会误绑**），但「OWNER 显式迁移」这个交付项实际上不可执行。
- **是否真实复现**：迁移顺序与唯一索引的冲突已用 PGlite 复现；「线上 owner 行 email 是否为 NULL」需要一条只读查询（见 §五）。
- **最小修法**：
  1. 加一条幂等迁移或文档化的运维步骤，把 2 条 legacy OWNER 的 `email` 从 Clerk 回填（`update public.profiles p set email = <verified pku email> where clerk_user_id = ... and email is null`）；
  2. 文档明确：OWNER 的 Supabase 账号必须由 Dashboard/Admin API 预建（不得走 `/api/auth/register`），并把这一步写成命令；
  3. 给 settings 页加一个 OWNER 专属「绑定 Supabase 账号」按钮（调用现成路由），否则该路由等于不可达；
  4. 顺带修 M-N2，让「同邮箱已有 profile」走明确的 409 文案。

### H-N2（高，功能；非越权）PKU_Course：成员任务在共享账本上会被 OWNER 任务挤出窗口，导致成员同步静默不推进

- **位置**：`apps/worker/src/commands.mjs:240-247`（`nextActionableTask` 先 `store.listTasks({limit:200})` 再 `filter(owner_id)`）；`packages/store/src/ledger.mjs:111-118`（SQL 为 `ORDER BY priority DESC, id LIMIT ?`）；
  控制面 `apps/control/src/server.mjs:115` 同样先按全局取 300 行再过滤。
- **可复现条件**：成员与 OWNER 共用同一个账本（`deploy/control-env.example` 把 `COURSE_LEDGER_PATH` 指向 `~/.course-worker/ledger.sqlite`；成员子进程继承它，`jobs.mjs:39`）。OWNER 任务 `priority=100`、成员 `priority=10`（`ledger.mjs:220-223`），排序后 OWNER 全在前。
- **复现证据**（`/tmp/a24/probe-member-starvation.mjs`，真实 SQLite 账本 + 真实 `nextActionableTask`）：
  ```
  owner tasks in ledger:   50 | member tasks: 1 | nextActionableTask(ownerId=member) -> …::member-lesson
  owner tasks in ledger:  199 | member tasks: 1 | nextActionableTask(ownerId=member) -> …::member-lesson
  owner tasks in ledger:  200 | member tasks: 1 | nextActionableTask(ownerId=member) -> NULL (member task invisible)
  ```

- **最小修法**：`nextActionableTask` 与 `/v1/tasks` 把 owner 过滤下推到 SQL：
  `store.listTasks({ ownerId, limit })`（SQL 已支持 `? IS NULL OR owner_id = ?`）；OWNER 侧若要同时看历史遗留行（`owner_id IS NULL`），用第二条查询按 `resource_class='owner' AND owner_id IS NULL` 合并。

### M-N4（中）PKU_Course：MEMBER 与 OWNER 同 UID、同 cgroup，一个成员的内存压力会波及 control 与所有成员

- **位置**：`deploy/course-control.service:20-25`（`MemoryMax=900M`、`CPUQuota=80%`、`TasksMax=256` 覆盖 control 主进程 + 所有 MEMBER 子进程，含 Chrome/ffmpeg）。
- **实际影响**：成员任务的内存压力触发 cgroup OOM 时，被杀的可能是 control 主进程本身 → 队列与扫码会话（都在内存）全部丢失，其他成员正在跑的任务一起死（`Restart=on-failure` 会拉起进程，但状态不可恢复）。当前没有 per-owner/per-job cgroup。
  另外**同 UID 意味着文件系统边界没有隔离**：成员子进程可以用绝对路径读 `~/.course-worker/env`（OWNER 凭据）和别的成员账户目录。

- **最小修法**（择一，按投入）：每个 job 用 `systemd-run --scope -p MemoryMax=…` 起独立 scope；或至少把 control 主进程单独放进更小配额的上层 cgroup，并给成员任务更小的 `MemoryMax`；文档补一句「MEMBER 与 OWNER 同 UID，未做文件系统隔离」。

# 九、已知可接受边界（不计入阻断）

1. R2 配额在并发上传下可能短暂超额，未 complete 的对象可能成为孤儿（需定期清理）；**未发现跨 owner 访问路径**。
2. MEMBER job token 默认 1 小时，过期后写回失败、任务可重跑；不做自动续签（有意设计）。
3. 任务与扫码会话仍在内存；control 重启由 `KillMode=control-group` 一起收掉子进程，历史丢失。
4. MEMBER 全局串行（1 个）；`max_active_jobs/owner_reserved/hls_concurrency` 已弃用且不再从 API 返回。
5. `/_control/` 依赖 HMAC + 可选 Cloudflare Access，没有 mTLS；单 control 实例假设成立（nonce 表在进程内）。
6. 提醒「先发信后置状态」未做 claim 锁，极端并发下可能重复发信。
7. MEMBER 与 OWNER 同 UID、同 cgroup（未做文件系统/进程级沙箱）。
8. 生产迁移未执行；本报告的数据库证据来自 PGlite 上**同一份迁移代码路径**的重放，不等于生产已具备该状态。
