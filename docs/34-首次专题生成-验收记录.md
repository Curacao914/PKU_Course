## 一、① Cloudflare Bypass：被权限挡住

**现状诊断（只读）**：
- 该 zone（`law-tech.dev`，id `d6a902cf29c624192d326a2abae68e74`）确实会缓存登录态的 `/`：origin 直连 3101 返回 `cache-control: private, no-store`，经 Cloudflare 后变成 `private, max-age=300` 且 `cf-cache-status: HIT / age: 23`（说明 zone 上有缓存规则覆盖源站头）。
- 手上的 `CLOUDFLARE_PURGE_TOKEN` 只有 **purge** 权限：
  ```
  GET /user/tokens/verify                                  → 200 active
  GET /zones/<id>                                          → 200 (law-tech.dev / Free)
  GET /zones/<id>/rulesets                                 → 403 (10000 Authentication error)
  GET /zones/<id>/pagerules                                → 403 (9109 Unauthorized)
  GET /zones/<id>/settings | /settings/browser_cache_ttl   → 403
  GET /zones/<id>/rulesets/phases/http_request_cache_settings/entrypoint → 403
  ```
  → **无法创建/读取 Cache Rule 或 Page Rule**，也无法读取 zone 缓存设置。

**需要你二选一**：
1. 给一枚带 `Zone → Cache Rules → Edit`（以及 `Zone → Page Rules → Edit`，视你用的是哪种规则）的 token；或
2. 在 Cloudflare 控制台按下面内容加一条规则（Cache Rules → Create rule）：
   ```
   名称：course dynamic entry bypass
   匹配（表达式，Edit expression 模式下粘贴）：
   (http.host eq "course.law-tech.dev" and (
       http.request.uri.path eq "/" or
       starts_with(http.request.uri.path, "/_auth/") or
       starts_with(http.request.uri.path, "/admin") or
       starts_with(http.request.uri.path, "/api/account/") or
       http.request.uri.path eq "/mcp"
   ))
   动作：Bypass cache
   ```
   `/assets/*`、`/md/*` 等静态路径**不在**表达式内，保持原有缓存 ✓（与你的要求一致）。
   注意顺序：若已有一条"Cache Everything"的旧规则，把这条 Bypass 放在它**上面**。

**当前残余风险（不阻断）**：被缓存的只是与账号无关的静态壳（OWNER 与 MEMBER 拿到的 HTML 逐字节相同、不含邮箱/UUID/课程名，数据全部由 `/api/account/*` 运行期取且那些接口 `no-store`）；未登录访问 `/` 仍是 302 且 `cf=BYPASS`。所以现在没有跨账号数据泄漏；但一旦将来把账号信息渲染进 HTML 就会命中缓存，建议尽快加规则。

## 四、两项不达标（**未自行修改**，按要求交回）

### F1（功能缺口）MCP 发现不了专题
`packages/notes-mcp/src/service.mjs:156-187` 已经把 `topics`/`topicCount` 放进 get_course 的返回对象，但工具结果只带 **文本**：
```
result 顶层键 = content,isError        （无 structuredContent）
get_course 文本 1041 字：含"专题"=false、含"topic:"=false、含"fetchId"=false
list_courses 文本里也没有 topicCount
```
`render.mjs` 里没有任何 topics 渲染分支，工具也没有 outputSchema → 这些字段在最后一跳被丢掉。后果：客户端拿不到 `fetchId`，`fetch(topic:<id>)` 实际不可达（虽然接口本身能用）。
修法方向（不在本轮改动范围）：给 get_course 的文本渲染补一段专题清单（title + 覆盖课次 + `topic:<id>`），或给该工具加 outputSchema 让 structuredContent 承载 topics。

### F2（数据缺陷）OWNER 发布后私有笔记丢 `checksum`，导致专题被误判 stale
- 代码：`apps/worker/src/commands.mjs:2967` 在写回个人空间时传 `checksum: record.checksum`，但 `record` 来自 `buildNoteRecord(...)`（2940-2956 行构建），**该函数不产出 `checksum`**——库记录的 checksum 是后面 `markdownBytesChecksum(markdown)`（2734 行）另算的。于是写回的 `metadata.checksum` 变成空。
- 证据链：数据库里 `notes/国际刑法学/2026-09-09第10-12节` 的 `metadata.checksum = null`（`updated_at 2026-10-04T06:23:52Z`，正好是本次部署验收里那一节"重发写回"的时间），而同课程的 09-16、09-23（只经导入、未重发）都有正常 checksum。
- 后果：`store.mjs` 的 `privateTopicStatus` 用 `note.metadata.checksum` 与专题里记录的 checksum 比对 → 含该课次的两个专题被判 **stale**（正是验收里那 2 条"待更新"，但内容其实没变）。
- 修法方向（不在本轮改动范围）：写回时用 `contentChecksum`（或 `markdownBytesChecksum(markdown)`）而不是 `record.checksum`；或让 `buildNoteRecord` 一并产出 checksum。修好后重新发布一次那节课即可消除误报（专题内容无需重做）。
