## 二、做法

走仓库自带的设计路径，不手工改产物、不手工挑 SQL 之外的捷径：

1. **构造 staging 目录**（``/.course-worker/backfill/staging/<replayKey>/`）
   从**当前发布库**里取出这一篇的正文、简报、关键词、主题，写成 `publish --from` 期望的三件套：
   `<课次>.md` + `notes-run-summary.json` + `brief.json`（带 `sourceChecksum`）。
   —— 这一步是关键：**不能直接用 `replays/<key>/transcript` 当 `--from`**（原因见 §五 发现 1）。
2. **6 篇缺一页纸**：`course publish --from <staging> --replay-key <key>`。
   publish 的 `resolveDerived` 发现 `onepage.json` 不存在 → 调模型补生成 → 写回目录 → 连同 `sourceChecksum` 一起发布（输出 `onepage: {applied: true, reason: 'generated'}`）。
3. **补来源映射**：本轮生成的一页纸**没有带 sourceMap**（6/6 都是 0 条），因此按设计再跑
   `course sourcemap --course <课程> --lesson <课次> --model --max-cost-cny 0.60 --write`（免费词法路径 + 模型补块，逐块逐字核对）。
4. **2 篇缺主题**：
   - 刑事执行法 09-14：`replay` 的 `brief.json` 里本来就有 `theme`（当年生成过，只是没进发布库）→ staging 里带上它重发即可，**不进模型**；
   - 刑事执行法 09-21：任何地方都没有主题 → 用 `course brief` 在**临时目录**里重新生成一次（1 次模型调用），**只取 theme 字段**，已发布简报正文一个字不动。
5. **写回 replay 工件**：把发布库里的简报/一页纸/映射写回 `replays/<key>/transcript/{brief,onepage}.json`，让"源工件"和"已发布内容"重新一致（下一次 publish 不会再被旧工件覆盖）。写前全部备份。
6. 全程 `contentChanged: false` → **没有触发任何通知**（日志里没有任何 notify/delivery 行）。

## 五、过程中的三个发现（两个已就地修正，一个建议改代码）

1. **replay 里的简报工件是陈旧的**（真实踩到）：直接 `publish --from replays/<key>/transcript` 会把发布库里**更新**的简报覆盖回旧版本（国际刑法学 09-09：简报 300→265 字、`bound` 由 true 变 false、主题与关键词被换掉）。
   已处理：从备份整库还原（`library.json.before` + `publish --rebuild`，diff 确认逐字节回到原状），改用 §二 的 staging 方案；并把**当前发布库的简报写回**这 8 个 replay 工件，消除"下次重发又被覆盖"的隐患。
   **建议**：`publish` 在写入记录前，至少把"工件简报与发布库简报不一致"打印成显式警告（现状只在 reason 里写 `ok`/`unbound`，人看不出内容被换过）。
2. **当前代码生成的一页纸不带 sourceMap**（6/6 都是 0 条，而历史 8 篇都有）：说明 `ONEPAGE_SCHEMA` 里的 `sourceMap` 在实际生成里常被模型漏掉，而被 `stampSourceMap` 判空丢弃后**不会重试**。
   已处理：用 `course sourcemap --model` 补（每篇 7—41 条，`generatedBy: lexical-overlap+model`）。
   **建议**：`generateOnepage` 在 `sourceMap` 为空时把它当成一次"未完成"重试一次（与超字数重试同一档），否则每条新笔记都要人多跑一步。
3. **两个记账字段会被重发悄悄丢掉**：
   - `notifyPolicy: 'none'`（`publish --no-notify` 留下的**长期**"这篇不要通知"）——`resolveNotifyPolicy` 会读 `stored`，但只有 `reason === 'flag'` 时才写回，于是"不带 flag 的重发"会把这条**持久决定**丢掉（下一次内容变化就可能推送）。已用 `publish --no-notify` 把这 2 篇恢复；
   - `notifiedAt`（入队后留下的时间戳）不在 `buildNoteRecord` 的字段里，任何重发都会丢。已按备份值恢复并 `--rebuild`。
   **建议**：这两处都在 `publish` 侧收口（policy 只要解析为 none 就写回；`notifiedAt` 从 `previous` 继承）。
