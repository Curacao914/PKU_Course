# 17 · 内容生命周期：版本、派生产物与原子发布

> 2026-10-02。本文件描述**当前目标形态与已落代码**。  
> 9 月份的 `docs/04`—`docs/16` 保留为开发记录；其中写着“尚未实现”的事项若与本文冲突，以本文与当前源码为准。

## 1. 一条主线

系统现在把内容分成两类：

1. **事实源**：单课笔记。它绑定转录稿与课件，是所有公开派生内容的唯一事实来源。
2. **派生物**：简报、一页纸、来源映射、章级整合、知识索引、语义向量。它们必须声明或能够核对自己依赖的是哪一版单课笔记。

生命周期：

```
转录 / PPT
    ↓
单课笔记 revision
    ├── brief
    ├── onepage
    │     └── sourcemap
    ├── metadata
    │     ├── 概念索引
    │     ├── 法条索引
    │     └── 案例索引
    ├── configured integrations
    └── semantic embeddings
             ↓
       site release staging
             ↓
       完整性与版本校验
             ↓
        site symlink 原子切换
```

核心规则：**宁可暂时少一个派生能力，也不允许旧派生物冒充新正文的结果。**

## 2. 内容发布事务

### 2.1 目录形态

完成一次性迁移后：

```
~/.course-worker/
├── site -> site.releases/release-20261002...
└── site.releases/
    ├── legacy-...            # 迁移前的原站点，天然成为第一份可回滚版本
    ├── release-...           # 已完成发布
    └── .staging-...          # 只在构建中存在；失败即删除
```

`COURSE_SITE_ROOT` 仍然是 `~/.course-worker/site`，site/admin 两个进程的 systemd 配置不需要换路径。
Node 每次打开文件都会跟随当前 symlink，因此日常内容切换不要求重启服务。

### 2.2 每次发布的提交协议

release 模式下，普通 `course publish` 与 `publish --rebuild` 都按同一顺序：

1. 在 `site.releases/.staging-*` 生成**完整站点**；
2. 把本次对应的 `library.json` 一并放入 staging；
3. 校验 `index.html / notes.json / library.json`，并逐篇检查正文 HTML、Markdown、一页纸页面是否齐全；
4. 再检查一次“开始构建时读到的 library revision 是否仍然是当前版本”，防止并发发布把别人刚发的课覆盖回去；
5. staging 封存成 `release-*`；
6. 建临时 symlink，再用单次 POSIX `rename` 替换 `site`；
7. 旧 release 保留，可用 `course publish --rollback-site --yes` 回到上一份完整快照。

因此读者只会看到**完整旧版**或**完整新版**，不会看到“新 library + 旧页面”“新正文 + 半套索引”这种中间状态。

### 2.3 旧部署兼容与一次性迁移

代码合并以后，若生产上的 `~/.course-worker/site` 还是实体目录，普通 publish **继续走旧路径**，
不会自动改变部署拓扑。

迁移必须显式执行，而且要先停两个站点进程：

```bash
systemctl --user stop course-site.service course-admin.service
node ~/course-runtime/apps/worker/bin/course.mjs publish --migrate-site-root --yes
systemctl --user start course-site.service course-admin.service
```

迁移后如果某次内容发布需要回滚：

```bash
node ~/course-runtime/apps/worker/bin/course.mjs publish --rollback-site --yes
```

命令会先重新校验回滚目标，再原子切换 symlink，并定向清理新旧两版涉及的 CDN URL。

迁移动作只是：

```
site/  →  site.releases/legacy-.../
site   →  site.releases/legacy-...   # symlink
```

不重写任何内容、不调用模型、不发通知。迁移命令重复执行是幂等的。

> 这一步需要服务器权限。仓库侧只能准备代码与测试，不能把“代码已实现”写成“生产已迁移”。

## 3. 派生物失效链

### 3.1 简报与一页纸

已有规则继续保持：

- `brief.sourceChecksum` 必须与当前正文的规范化 checksum 一致；
- `onepage.sourceChecksum` 同理；
- 不同源时 publish 默认中止；
- 只有显式 `--regenerate-derived` 才允许调用模型重做。

因此修改历史正文后，不可能悄悄挂着旧简报或旧一页纸重新上线。

### 3.2 一页纸来源映射

source map 同时绑定：

- 单课正文：`note.slug + note.checksum`
- 一页纸：`onepageChecksum`

正文或一页纸任何一边变化，整份旧映射失效；单条摘录、小节或块对不上时，只丢该条。
映射生成仍遵循“免费证据先跑，模型只补缺口，程序逐字核对摘录”的原则。

### 3.3 语义向量

每一条 embedding 绑定**小节 fingerprint**；检索时 fingerprint 对不上就跳过该向量。

release 模式会把已有 `embeddings.json` 带进新 release，但安全边界仍在**小节 fingerprint**：

- 正文没变的小节：旧向量继续可用；
- 正文变化、删除或重新分节：旧向量因为 fingerprint / section id 对不上，被检索层直接跳过；
- 下一次 `course embed --max-cost <元>` 能读取这份旧索引，复用未变化向量，只为变化部分重新付费。

因此“继承索引”不等于“相信旧索引”：旧文件只是缓存容器，真正能参与召回的仍然必须逐小节通过当前正文指纹校验。

## 4. 章级整合从“临时命令”变成长期产物

### 4.1 manifest

默认清单：

```
~/.course-worker/integration-manifest.json
```

每一项固定：

```json
{
  "id": "刑事执行法::罪刑均衡与以刑制罪",
  "course": "刑事执行法",
  "topic": "罪刑均衡与以刑制罪",
  "lessons": ["2026-09-07第5-6节", "2026-09-14第5-6节", "2026-09-21第5-6节"],
  "enabled": true
}
```

**lessons 必须是显式数组。** 后来同一门课新增课次，不会自动进入旧章节，防止章节范围随学期推进悄悄漂移。

### 4.2 第一次定章

```bash
course integrate \
  --course 刑事执行法 \
  --lessons 2026-09-07第5-6节,2026-09-14第5-6节,2026-09-21第5-6节 \
  --topic 罪刑均衡与以刑制罪 \
  --save
```

`--save` 必须给明确 `--topic`。它保存的是**本次真正解析到的课次**，不是“以后这门课的全部课”。

需要自定义稳定 ID 时可加 `--id`；需要另放清单时可加 `--manifest`。

### 4.3 后续自动维护

手工全量重建：

```bash
course integrate --configured
course integrate --configured --id 刑事执行法::罪刑均衡与以刑制罪
```

普通 publish 如果检测到正文内容变化，会读取默认 manifest，只重建那些**明确包含当前课次**的整合。
这一步是确定性抽取，不调模型、不花钱。

如果某份配置因为课次被删除/改名而无法重建：

- 单课正文仍然可以正确发布；
- 错误会出现在 publish 结果里；
- 旧整合不会被伪装成新版本；
- `course artifacts` / `course reconcile` 继续把它报为 stale，等人工修清单。

## 5. 历史内容修复应走的路径

以后修 ASR 错词、老师观点、案例事实或旧笔记结构时，标准流程应是：

```
回查转录 / PPT
    ↓
局部修改单课正文
    ↓
新正文 checksum / section fingerprint
    ↓
brief / onepage 不同源 → 阻止误发布或显式重生成
sourcemap 不同源      → 失效 / 重建
configured integration → 自动重建
semantic embeddings    → 旧索引随版保留，变更小节按指纹失效并增量重建
metadata indexes       → 随站点构建重算
    ↓
完整 staging 校验
    ↓
原子切换上线
```

这条路径的意义是：**以后修一处内容，不需要靠人记住“还有哪五个地方要顺手更新”。**

## 6. 当前仍然保留的人为决定

以下事情没有被“自动化”偷走：

1. 第一次决定一章包含哪些课次；
2. 是否启用 `integrate --live`（目前仍未实现；若以后实现，会单独受模型预算与出处审查约束）；
3. 是否给公开站点配置独立的 embedding key、从而启用公开语义回退；
4. source map 覆盖不足时，是否批准额外模型预算；
5. 历史内容本身怎么改——必须先回查原始依据，系统只负责传播版本变化。

## 7. 测试边界

本轮新增测试覆盖：

- staging → 校验 → seal → symlink 切换；
- 第二次切换后旧 release 仍存在，可回滚；
- 旧实体 site 的一次性迁移与幂等；
- 普通发布不得偷偷迁移旧实体目录；
- 不完整 staging 不得上线；
- integration manifest 去重、固定课次范围、按受影响课次筛选；
- `integrate --save` 与 `integrate --configured` 的真实命令级往返；
- `publish --migrate-site-root` 必须显式 `--yes`。

GitHub CI 继续执行根目录 `npm test`。生产迁移完成后还需要补一次真实服务器验收：
两个 healthz、真实域名读旧/新页面、发布过程中并发请求不出现 404、以及手工切回上一 release。
