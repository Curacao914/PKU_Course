## 3. 高 / 中 / 低

### H1（高）控制面全局 secret 落在每个成员子进程里
`apps/worker/src/commands.mjs:2200-2215`（`publishPrivate`）从**子进程环境**读 `COURSE_CONTROL_SECRET`，
再带着 `x-course-owner-id: <自己>` 调 `/v1/internal/private-note`。私有发布需要它，所以不能简单删掉；
但用一个**全局** secret + 调用方自报 owner 头，等于"任何拿到 secret 的进程可以冒充任意用户"。
建议：控制面为每个 owner 签一个**可撤销的 per-owner token**（存 Supabase，随账号注销失效），
子进程只拿自己那一枚；`x-course-owner-id` 只作为交叉校验，不再作为授权依据。

### H2（高）`/_control/` 公开暴露，唯一屏障是静态 secret
`deploy/nginx-course.conf.example:54-67` 在**公开站点**的 server 块里把 `/_control/` 反代到 3102，
没有 IP 白名单、没有 `limit_req`、没有独立 vhost。控制面因此对全网可达，安全完全取决于
`COURSE_CONTROL_SECRET` 的长度与保密（代码里**没有强度校验**：`server.mjs:29-49` 只做等长比较）。
建议：至少加 `limit_req` + 只允许 law-tech 出口；更好的是用独立域名/端口、或加一层 mTLS/HMAC 时间戳签名。

### H3（高）凭据密文未绑定 owner 与字段（AES-GCM 无 AAD）
`apps/control/src/crypto.mjs:16-39`：随机 IV、GCM 认证都对，但**没有 AAD**。拿到数据库写权限的人
可以把 A 的 `ciphertext/iv/tag` 整段搬到 B 的行里，B 解出来就是 A 的密钥（不会被发现）。
建议：加密/解密时带上 `AAD = ownerId + ':' + provider`（`encryptFields` 已经有 prefix，顺手就能传）。

### M1（中）配额列写了不读；队列全局串行
`user_resource_limits.max_active_jobs` 与 `owner_reserved` 只在 `store.mjs:141-142` 写默认值，
**没有任何地方读**（全分支搜索确认）。实际并发控制是 `jobs.mjs` 里的单一 `active` 槽——**全局串行**，
于是一个成员 3 小时的同步会挡住所有其他成员（队头阻塞），而 DB 里写着 `max_active_jobs=4/1`。
要么实现按 owner 的并发限制，要么把这两列删掉并在文档里写明"成员任务全局串行"。

### M2（中）任务记录在进程内存
`jobs.mjs:10-12` 的 `jobs/queue/active` 都是模块级内存。控制面重启 → 历史消失；如果重启时子进程还在跑，
会出现"孤儿子进程 + 新任务"同时操作同一批账本任务（租约能挡住一部分，但不是设计上的保证）。
建议：把 job 状态落到 Supabase（你们已经有表），至少落 id/owner/kind/status/时间。

### M3（中）R2 配额检查有 TOCTOU
`r2.mjs:56-85`：presign 前查用量 + 请求大小，两项分两次读，没有预留；`complete`（`server.mjs:246-269`）
事后才复核并删除超标对象。上传后**不调用 complete** 的对象不会被复核，但会计入用量（`usage()` 全列前缀）——
所以最坏情况是"额度被占满 + 垃圾对象"。建议：预签名用 S3 **POST policy + content-length-range**
（由 S3 强制大小），并在 `complete` 之外再加一个"未 complete 的孤儿对象"定期清理。

### M4（中）课程勾选未校验
`/v1/account/pku/selection`（`server.mjs:195-203`）接受任意字符串数组，不校验这些 key 是否来自
**该用户自己扫描到的课程**。当前影响有限（用的是该用户自己的教学网会话，选到别人的课也扫不出来），
但在 B1 修好之前，它正好给"用 OWNER 凭据登录"这条路径提供了可选的越界目标。建议：只接受
`pku_connections.scanned_course_keys` 的子集。

### M5（中）控制面整体没有测试
`apps/control/` 下**没有任何 `*.test.mjs`**（`ls apps/control/src/*.test.mjs` → 不存在），而仓库的约定是每个模块配测试
（`apps/*/src/*.test.mjs` 会被 `npm test` 收走）。这恰好覆盖了三个最该被钉住的点：
**owner 隔离**（B1 就是这类）、**配额计算**、**任务排队与优先级**。
建议至少补：`crypto`（AAD 往返 + 篡改检测）、`jobs`（成员环境白名单、owner 让位、串行）、
`r2`（配额边界）、`server`（鉴权 401 / owner 头校验 / 材料 key 前缀）。

### 低
- **L1** `deploy/release.sh:128-131`：`control` 单元**跳过**角色/内容检查（site/admin 都有）。至少校验单元里存在 cgroup 与 127.0.0.1 绑定。
- **L2** `jobs.mjs:37`：`COURSE_DOWNLOAD_CONCURRENCY` 被写死为 1（`Math.min(1, …)`），与 `user_resource_limits.hls_concurrency` 无关——列存了不生效。
- **L3** `qr.mjs:5`：扫码会话在内存，控制面重启即丢（用户那边表现为"二维码突然失效"）。
- **L4** `jobs.mjs:14-16` `safeOwner()` 把非字母数字替换成 `_`：两个不同 owner（如 `a+b` 与 `a_b`）会映射到同一个目录名。当前 owner 是 UUID，理论风险，但建议直接用 `crypto.createHash('sha256').update(ownerId).digest('hex').slice(0,32)`。

## 2. 严重项：私人笔记所在的表没有 RLS、也没有 revoke

**证据：**
- 表在 `lib/db/migrations/20260625_reading_notes.sql:1` 创建（`notes` 有 `owner_id`），
  `lib/db/migrations/20260625_reminders.sql:1,15` 创建 `reminders` / `reminder_events`。
- 全仓迁移里 `enable row level security` 只出现在 `profiles/captures/schedule_items`
  （`20260624_schedule_cloud.sql:52-54`）、`class_notice_*`（`20260917...:50-51`）、
  `signup_invites/provider_credentials/pku_connections/user_resource_limits`（`20261002...:76-79`）、
  `course_user_materials`（`20261003...:18`）。
  **`notes` / `reminders` / `reminder_events` 一个都没出现**；全仓也**没有任何 `create policy`**。
- 而 `lib/supabase/client.js` 把 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`（= anon key）打进浏览器。
- 新的 `course_user_materials` 迁移里作者已经写了 `revoke all ... from anon, authenticated`
  ——说明他们知道 Supabase 在 `public` schema 上对 `anon/authenticated` 的默认授权是"全给"。
  同样两行**没有**加到 `notes`/`reminders` 上。

**会被怎样利用（前提：默认授权仍在）**：任何拿到站点的人都能从浏览器 bundle 里取到 anon key，然后
```
curl "$SUPABASE_URL/rest/v1/notes?select=id,title,body_markdown,owner_id" -H "apikey: <anon>" -H "authorization: Bearer <anon>"
```
直接读**所有用户**的私人课程笔记与阅读笔记；`reminders` 同理（个人日程）。写入/删除同样可能。

**为什么"anon key 一定拿得到"**：`app/sign-in/sign-in-form.jsx:5` 引入的是浏览器端客户端
（`lib/supabase/client.js` → `createBrowserClient(NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY)`），
所以这两个公开值在登录页的 bundle 里就有；即便不用页面，也能直接从任意地方调 PostgREST（只需 apikey 头）。

**为什么修起来很安全**：应用侧读这些表的地方全部走 service role
（`app/api/notes/route.js:44-52`、`app/api/course-notes/route.js:8-14` 都是 `createServiceClient()`），
**不依赖 RLS 放行**。所以照抄 `course_user_materials` 的两行即可，不会破坏现有页面。

**修法：**
```sql
alter table public.notes               enable row level security;
alter table public.reminders           enable row level security;
alter table public.reminder_events     enable row level security;
revoke all on public.notes             from anon, authenticated;
revoke all on public.reminders         from anon, authenticated;
revoke all on public.reminder_events   from anon, authenticated;
```
（若日后要让浏览器直连，再按 `auth.uid() = owner_id` 加 policy；现在全走服务端，直接全禁最省事。）

**确认命令（在 Supabase SQL Editor 跑，30 秒）：**
```sql
select relname, relrowsecurity from pg_class c
  join pg_namespace n on n.oid = c.relnamespace
 where n.nspname = 'public' and relname in ('notes','reminders','reminder_events');

select table_name, grantee, privilege_type
  from information_schema.role_table_grants
 where table_schema = 'public' and grantee in ('anon','authenticated')
   and table_name in ('notes','reminders','reminder_events');
```
第一条若 `relrowsecurity = false`、第二条若能查到行 → 就是上面的漏洞，按修法补两行即可。

## 3. 高 / 低

### H1（高，需确认项目设置）邮箱绑定的账号关联缺少"已验证"前置
`lib/server/auth.js:19-51`：Supabase 用户第一次登录时，如果 `auth_user_id` 没绑过，
就**按邮箱**在 `profiles` 里找 `auth_user_id is null` 的老资料，并**直接绑定**上去（继承其 `role`）。
这条路径本身是给"旧 Clerk OWNER 迁移"用的，写得很克制（`is('auth_user_id', null)` 条件更新，避免覆盖已绑定），
但**没有校验 `user.email_confirmed_at`**。若 Supabase 项目把「Confirm email」关掉，
那么"用别人的北大邮箱 + 有效邀请码注册"就能直接拿到那个邮箱对应的旧资料（可能 `role='owner'`）。
- 修法：绑定前要求 `data.user.email_confirmed_at`（或 `confirmed_at`）存在；顺带在该分支里再跑一次 `isPkuEmail`。
- 确认：Supabase → Authentication → Providers → Email，「Confirm email」必须开着；
  或直接看 `select email_confirmed_at from auth.users where email = '<某个旧 owner 的邮箱>'`。

### L1（低）邀请码回退是"按 id 减 1"
`lib/db/migrations/20261003_atomic_signup_invites.sql:24-34` + `app/api/auth/register/route.js:120-127`：
注册失败会 `release_signup_invite(invite_id)` 把 `used_count` 减 1。消费是原子的（单条 UPDATE，条件都在 WHERE 里 ✓），
回退也只会退自己那一次 ✓，因此**不能用来多发账号**；但"能反复触发失败"的人可以让一个 `max_uses=1` 的码长期保持可用状态。
不算漏洞，记一笔；要更严谨可给 `signup_invites` 加一列 `reserved_at` 并在回退时校验时间窗。

### L2（低）双会话并存
`lib/server/auth.js:63-80`：先试 Supabase、再试 Clerk，两者都要 `status='active'` 且 `requireOwner()` 再查 `role`，
所以不存在"Clerk 路径绕过新鉴权"；风险只是**同一个 OWNER 有两个身份**时的注销语义（在一边注销，另一边仍有效）。
建议在迁移期文档里写清"旧 Clerk 入口的退役时间"。

## 10. law-tech 深度审计（子代理）+ 我的独立复核

子代理做了一轮更细的通读（迁移、路由、服务端、中间件、组件），下面是**合并后**的结论。
每条标了「✅ 我复核过（附证据）」或「⚠️ 子代理报告、我未复核」——标 ⚠️ 的请当成"需要你确认的疑点"，不要直接当结论。

### 10.1 阻断（✅ 我复核过）

**迁移与线上库不一致：`profiles` 的 `status` / `email` / `last_seen_at` 从来没有被任何迁移创建。**
- 表定义只有 `id, clerk_user_id, display_name, role, created_at, updated_at`（`lib/db/migrations/20260624_schedule_cloud.sql:3-10`）；
- 本轮迁移只补了两列：`add column if not exists auth_user_id uuid, add column if not exists notification_email text`
  （`lib/db/migrations/20261002_auth_course_v2.sql:3-5`）；
- 而代码在读写这三列：`lib/server/auth.js:24,34,46,57,70`（`select … email, status …`）、
  `app/api/auth/register/route.js:96-103`（insert `email`/`status`）、`app/auth/confirm/route.js:17-23`（update `email`/`status`/`last_seen_at`）。
- 后果：**用迁移从零建的库跑不起来**——注册/登录/确认整条链会因 `column does not exist` 失败。
  线上能跑，说明这几列是手工加过或早期迁移留下的 → **仓库不是数据库的真相来源**，下次环境重建必踩。
- 修法：补一条幂等迁移（三个 `add column if not exists` + 存量行回填 `status='active'`），把线上已手工做过的改动写进仓库。

### 10.2 高（✅ 我复核过）

**H4 `PUT /api/schedule/items` 的批量 upsert 没有 owner 守卫 → 可改写/夺走别人的日程条目。**
`app/api/schedule/items/route.js:44`：`upsert(rows, { onConflict: 'id' })`，`id` 来自请求体（`route.js:22-27` 只校验 uuid 形状），
`owner_id` 被写成**调用者自己** → 知道/猜到别人的条目 uuid 就能把那行夺过来（对方条目消失、出现在攻击者日程里）。
注意同一函数里的**删除**是有守卫的（`route.js:35` `.eq('owner_id', profile.id)`）——说明这是漏了一处，不是设计选择。
修法：只更新 `id + owner_id` 都匹配的行，其余走插入。**这个文件在本 PR 改动范围内**（`git diff --name-only` 里有它），建议就在本 PR 修。

**H5 `POST /api/schedule/parse` 完全无鉴权，且会替调用者抓任意 URL。**
`app/api/schedule/parse/route.js:332-345`：没有任何 `requireCurrentIdentity/requireOwner`；
`fetchCommandLinkMetadata` → `fetchUrlMetadata` → `fetch(normalizedUrl)`（`route.js:119-132`），
`normalizeUrl` 只要求 `^https?://`（`route.js:77-79`）→ `http://127.0.0.1:3101/…`、`http://169.254.169.254/…` 都能打；
同时它用服务端 key 调模型（`route.js:296,311`）→ 匿名调用者可以**同时**做 SSRF + 烧模型额度。
这是既有代码（不是本 PR 引入），但本 PR 正在动同一批 schedule 路由，建议同批补鉴权 + 出站白名单（拒私网/回环/元数据地址）。
前端两个调用方（`components/TodayBoard.jsx:194`、`app/api/schedule/capture/route.js:9`）不受影响。

**H6 同邮箱自动绑定缺"已验证"前置**（与 §3 H1 同一条，子代理独立发现）：`lib/server/auth.js:29-51`。
另外它用 `ilike('email', email)`——邮箱含 `%`/`_` 会变通配，轻则误匹配、重则全表扫描。建议改 `eq` 且先要求 `email_confirmed_at`。

### 10.3 中（✅ 我复核过）

- **开放重定向（用执行证明）**：`app/auth/confirm/route.js:17`、`app/auth/callback/route.js:16` 都做
  `next.startsWith('/') ? next : '/desk/courses'`，而 `'//evil.com'` 满足 `startsWith('/')`。
  本机实测：`new URL('//evil.com','https://law-tech.dev')` → **`https://evil.com/`**。
