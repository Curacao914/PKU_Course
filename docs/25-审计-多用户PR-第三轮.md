## M-N2 ✅ CLOSED —— 重复邮箱走 409，异常不再回显数据库原文

- `app/api/auth/register/route.js:31-45` 在**消费邀请码之前**先查已有 profile，命中即 409（区分 owner/member 文案）→ 邀请码不会被白白吃掉；
  `:118-124` 把 5xx 文案统一成「注册暂时失败，请稍后重试」，不再回显 `error.message`。
- **残留（Low）**：预检用的是 `.ilike('email', email)`，而 `isPkuEmail` 允许 local part 含 `%` 与 `_`，因此它们是**通配符**。PGlite 实测：
  ```
  email ilike 'some%ne@pku.edu.cn'  → 命中 email = 'someone@pku.edu.cn'（% 被当通配符）
  email ilike '%'                   → 命中任意一行（可读出该行 role）
  email = 'some%ne@pku.edu.cn'      → 0 行（精确匹配不受影响）
  ```
  影响仅两处：真实含 % 的邮箱会被误判为「已存在」（自伤，不是绕过）；以及可探到**任意一条** profile 的 role。
  建议与 `auth-profile.js` 保持一致改用 `eq('email', email)` —— `idx_profiles_email_lower` 已经保证大小写不敏感的唯一性。

## M-N3 + L1 ✅ CLOSED —— 入口与发布链路收口

- **control 入口**（`apps/control/src/server.mjs:95-116`）：先按 `Content-Length` 与「签名信封」形状/时间窗做廉价校验，再读 body，最后才做完整 HMAC；

  ```
  正确 law-tech 签名            -> 通过鉴权（落到我的假 store 上 500，证明认证通过）
  ```

# 三、明确**不是**问题的几点（避免误报）

1. **`resource_class` 老数据**：列是 `NOT NULL DEFAULT 'owner'`，老行迁移后即为 owner 类，OWNER 侧不会漏任务（实测见上）。
2. **OWNER 的 `/v1/tasks` 不再显示「owner_id 等于自己、但类为 member」的任务**：当前没有任何代码路径会为 OWNER 造出这类任务（`discoverReplays` 只要带 `ownerId` 就写 member 类），故不是回归。
3. **`assertSignedRequestEnvelope` 被 verifier 复用**（`auth.mjs:24-33`）：两处判定条件完全一致，没有出现「预检一套、校验另一套」的漂移。
4. **`/health` 与 private-note 的鉴权顺序**：前者不读 body 直接返回；后者先验 token 再读 body，均未被本轮改动破坏。
5. **`owner-confirm` 的登录 CSRF**：攻击者即使拿到邮件链接，也会因缺少受害者的 Clerk 会话（且 OTP 在 Clerk 校验之后才消费）而失败；受害者点开攻击者的链接也不会绑上攻击者的账号。
