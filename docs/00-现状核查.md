#### 三条必须知道的既有事实

**(1) 仓库里其实有三条并行的笔记链路，别混淆：**

| 链路 | 入口 | AI 跑在哪 | 状态存哪 |
|---|---|---|---|
| A 生产自动（主线） | 教学网扫描 → 控制面入队 | **Next.js API 路由内（Vercel 函数）** | Supabase `course_jobs.preprocess_result.workflow`（单个 JSONB） |
| B 本地 CLI「好课」 | `build-pack.js` | 本地 Node（`model-exec-local.js`） | 本地目录 `working/` `output/` |
| C 浏览器工作台 | `/desk/courses` 导入 TextPack | 同 A | 同 A |

prompt 与模型调用因此存在**三份平行实现**（`lib/course/aiAdapter.js`、`scripts/course-worker/run-job.js`、`model-exec-local.js`）和两套环境变量契约（`COURSE_AI_*` vs `COURSE_MODEL_*`）。抽取时应收敛成一份 role→prompt→call 实现。

**(2) 模型调用跑在 Web 请求里，这是硬天花板。** `run-llm` 路由 `maxDuration: 300`，批内模型预算 `min(240s, 租约-30s) = 210s`。你本地那个未推的「课程 AI 超时修复」就是在跟这条天花板搏斗。**搬到自己的服务器、改成真正的后台 worker 之后，这条约束直接消失**——这是本次架构调整最大的实际收益。

**(3) 第二层租约存在 JSONB 里，有丢更新风险。** 阶段一队列（`course_pipeline_tasks`）用的是正经 SQL 行级租约（`for update skip locked`）；但阶段二的写作任务租约存在 `workflow.taskLeases` 里，靠读-改-写整个 JSONB blob，没有乐观锁。本机账本重做时应该把两层都做成正经的行级租约。
